How this site is built.

The architecture of the public sign-in static website, drawn in the C4 model. It is reachable from the internet, but every page asks for an Entra ID sign-in first, and only approved guests of the APEX tenant get in. One stack, deployed separately to dev, QA, UAT and production.

Who and what it touches.

C4 level 1, system context. The site is one software system per environment. External guests use it after signing in, and it depends on four systems it does not own.

What runs in each environment.

C4 level 2, containers. Every request passes the firewall and Front Door, then the Static Web App sends anyone not signed in to Entra ID. Everything reports into one Log Analytics workspace.

Four environments, one stack.

Each environment has its own settings file, its own state and, if needed, its own Azure subscription. These are the defaults.

Who gets in.

External people become B2B guests of the APEX tenant and sign in with their own work or Microsoft account. The app registration requires assignment, so only approved groups get past sign-in.

Invite
Addresses in guest_emails get a Microsoft invitation and join the site's users group.
Approve
The users group, plus any group in allowed_group_ids, is assigned to the app.
Sign in
Any page sends visitors who are not signed in to Entra ID; everyone not assigned is refused.
Remove
Taking someone out of the group stops their next sign-in.
Harden
Outside Terraform: Conditional Access with MFA for guests, and regular access reviews.

Watched from five regions.

Every environment gets the full monitoring set. Viewers and operators are Entra ID groups, limited to that environment.

Viewers
Open the dashboard, query logs, see metrics and alerts.
Operators
Everything viewers can do, plus change alerts, action groups and dashboards.
Availability
Tests from five regions on /healthz.html; alerts below the threshold.
Certificates
Tests fail when a TLS certificate has fewer than 14 days left.
Origin health
Alerts when Front Door cannot reach the site reliably.
Errors and latency
5xx rate, 4xx rate and edge latency, each with its own threshold.
Firewall
Alerts on a spike in blocked requests: an attack, or a rule to tune.
Risky changes
Deletions, firewall changes, new role assignments and removed locks.
Health and cost
Resource and service health, plus a monthly budget with forecast alerts.

How the Terraform is organised.

C4 level 3, components of the infrastructure code. One root module composes seven reusable modules; a wrapper script picks the environment so plans never share state.

Before the first deployment.

Everything that must be in place before the first deployment. Nothing has been applied to Azure yet, so dev is the first real test.

Tools
Terraform 1.9 or later, Azure CLI to sign in, Bash or PowerShell for the wrapper script, and Git.
Subscriptions
Best one per environment; at minimum production on its own, with dev, QA and UAT sharing one. If they share, turn on enable_service_health_alert and export_activity_log in only one of them. Use a Static Web Apps region (westus2, centralus, eastus2, westeurope or eastasia) and a billing type that supports budgets. The Web, CDN, monitoring, storage and cost services must be registered.
Terraform state
Run bootstrap/ once for the state storage account, then copy its output into each backend.hcl.
Deploying identity
Contributor, User Access Administrator for the monitoring roles, and Storage Blob Data Contributor on the state account. It also needs Entra ID rights to create app registrations and groups and to invite guests, or the identity team creates them and create_entra_app is set to false.
Settings
In each terraform.tfvars: subscription and tenant IDs, governance tags, alert recipients, viewer and operator groups, and the budget with its contacts, the guests or allowed groups, and custom domains. Replace every <…> placeholder.
Delivery pipeline
After the first apply, store the deployment token as AZURE_STATIC_WEB_APPS_API_TOKEN_PUBLIC_SIGNIN (one per environment) and the config output as SWA_CONFIG_JSON. Create the GitHub environments or Azure DevOps variable group used for approvals.
Tenant settings
The APEX tenant allows guest invitations, and cross-tenant settings do not block partners' home tenants. Conditional Access with MFA for guests and regular access reviews are recommended.
Custom domains
Access to the DNS provider to create a TXT validation record and a CNAME per domain.
Known blocker
The first plan on a new environment fails: the app's group assignments use the ID of the guest group created in the same run. Fix entra-app-auth before the first deployment.
Secret rotation
The sign-in secret rotates every 180 days, so the stack must be applied at least that often. A scheduled pipeline is advisable.

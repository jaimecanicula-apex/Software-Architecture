How the private site with storage is built.

The file library is not drawn on this page yet. Signed-in users share one private Blob container: the page signs the user in again with MSAL.js and calls storage directly with their own token, through a second private endpoint, with no account keys, versioning and soft delete, and malware scanning in uat and prod. The diagrams below show the site, sign-in and monitoring only. The full model, including storage, is in infrastructure/privately-accessible-static-website-with-storage/ARCHITECTURE.md and its draw.io files.

The architecture of the privately accessible static website, drawn in the C4 model. It is for internal APEX users only: no internet exposure, APEX sign-in on every page, and monitoring from inside the network. One stack, deployed separately to dev, QA, UAT and production.

Who and what it touches.

C4 level 1, system context. The site is one software system per environment, used only by people signing in with APEX Entra ID. It depends on four systems it does not own.

What runs in each environment.

C4 level 2, containers. The only way in is the private endpoint in the spoke VNet. The Static Web App has public access switched off, and telemetry travels over Private Link.

Four environments, one stack.

Each environment has its own network, settings file, state and, if needed, its own Azure subscription. These are the defaults.

Watched from inside.

Internet tests cannot reach a private site, so a probe inside the VNet does the checking. Viewers and operators are Entra ID groups, limited to that environment.

Viewers
Open the dashboard, query logs, see metrics and alerts.
Operators
Everything viewers can do, plus change alerts, action groups and dashboards.
Availability
The in-VNet probe requests the site every 5 minutes; alerts below the threshold.
Probe silence
Alerts when no result arrives for 15 minutes: the probe or the network path is down.
Private telemetry
Ingestion only through Azure Monitor Private Link; nothing crosses the internet.
Risky changes
Deletions, new role assignments and removed locks.
Health and cost
Resource and service health, plus a monthly budget with forecast alerts.

How the Terraform is organised.

C4 level 3, components of the infrastructure code. One root module composes eight reusable modules; a wrapper script picks the environment so plans never share state.

Before the first deployment.

Everything that must be in place before the first deployment. Nothing has been applied to Azure yet, so dev is the first real test.

Tools
Terraform 1.9 or later, Azure CLI to sign in, Bash or PowerShell for the wrapper script, and Git.
Subscriptions
Best one per environment; at minimum production on its own, with dev, QA and UAT sharing one. If they share, turn on enable_service_health_alert and export_activity_log in only one of them. Use a Static Web Apps region (westus2, centralus, eastus2, westeurope or eastasia) and a billing type that supports budgets. The Web, network, Container Apps, monitoring, storage and cost services must be registered.
Terraform state
Run bootstrap/ once for the state storage account, then copy its output into each backend.hcl.
Deploying identity
Contributor, User Access Administrator for the monitoring roles, and Storage Blob Data Contributor on the state account. It also needs Entra ID rights to create app registrations (or create_entra_app set to false), and Network Contributor on the hub if Terraform creates the peering.
Settings
In each terraform.tfvars: subscription and tenant IDs, governance tags, alert recipients, viewer and operator groups, and the budget with its contacts, the groups allowed to sign in, the network ranges (probe subnet at least /27) and DNS servers. Replace every <…> placeholder.
Delivery pipeline
After the first apply, store the deployment token as AZURE_STATIC_WEB_APPS_API_TOKEN_INTERNAL (one per environment) and the config output as SWA_CONFIG_JSON. Create the GitHub environments or Azure DevOps variable group used for approvals.
Platform team
Free IP ranges, the hub side of the peering, corporate DNS that resolves the site's private zone, and a decision on using the central Azure Monitor DNS zones.
User connectivity
VPN, ExpressRoute or office connectivity routed through the hub.
Probe image
Outbound internet to pull it from MCR, or a copy in an APEX container registry.
Deployment path
Verify in dev that uploads work with public access off; if not, the pipeline needs a runner inside the network.
Secret rotation
The sign-in secret rotates every 180 days, so the stack must be applied at least that often. A scheduled pipeline is advisable.

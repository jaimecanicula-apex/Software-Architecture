How the platform is built.

The architecture of the static website platform, drawn in the C4 model: who uses it, what runs, and how the Terraform that builds it is organised. One stack, deployed separately to dev, QA, UAT and production.

System context Containers Environments Monitoring Terraform stack

Who and what it touches.

The website is one software system per environment. People use it in three ways, and it depends on four systems it does not own.

What runs in each environment.

Every request passes the firewall and Front Door before it reaches the site. Everything reports into one Log Analytics workspace, which drives the alerts and the dashboard.

Four environments, one stack.

Each environment has its own settings file, its own state and, if needed, its own Azure subscription. These are the defaults.

Watched from five regions.

Every environment, dev included, gets the full monitoring set. Viewers and operators are Entra ID groups, and their access is limited to that environment.

Viewers
Open the dashboard, query logs, see metrics and alerts.
Operators
Everything viewers can do, plus change alerts, action groups and dashboards.
Availability
Tests from five regions on every public URL; alerts below the threshold.
Certificates
Tests fail when a TLS certificate has fewer than 14 days left.
Origin health
Alerts when Front Door cannot reach the site reliably.
Errors and latency
5xx rate, 4xx rate and edge latency, each with its own threshold.
Firewall
Alerts on a spike in blocked requests: an attack, or a rule to tune.
Risky changes
Deletions, firewall changes, new role assignments and removed locks.
Health and cost
Resource and service health, plus a monthly budget with forecast alerts.

How the Terraform is organised.

One root module composes five reusable modules. A wrapper script picks the environment, so a plan for one environment can never use another's state.

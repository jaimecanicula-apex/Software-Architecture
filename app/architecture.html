How the platform is built.

The architecture of the static website platform, drawn in the C4 model: who uses it, what runs, and how the Terraform that builds it is organised. One stack, deployed separately to dev, QA, UAT and production.

C4 level 1: System context C4 level 2: Containers Environments Monitoring C4 level 3: Terraform stack Prerequisites

Who and what it touches.

C4 level 1, system context. The website is one software system per environment. People use it in three ways, and it depends on four systems it does not own.

What runs in each environment.

C4 level 2, containers. Every request passes the firewall and Front Door before it reaches the site. Everything reports into one Log Analytics workspace, which drives the alerts and the dashboard.

Four environments, one stack.

Each environment has its own settings file, its own state and, if needed, its own Azure subscription. These are the defaults.

Watched from five regions.

Every environment, dev included, gets the full monitoring set. Viewers and operators are Entra ID groups, and their access is limited to that environment.

Viewers
Open the dashboard, query logs, see metrics and alerts.
Operators
Everything viewers can do, plus change alerts, action groups and dashboards.
Availability
Tests from five regions on every public URL; alerts below the threshold.
Certificates
Tests fail when a TLS certificate has fewer than 14 days left.
Origin health
Alerts when Front Door cannot reach the site reliably.
Errors and latency
5xx rate, 4xx rate and edge latency, each with its own threshold.
Firewall
Alerts on a spike in blocked requests: an attack, or a rule to tune.
Risky changes
Deletions, firewall changes, new role assignments and removed locks.
Health and cost
Resource and service health, plus a monthly budget with forecast alerts.

How the Terraform is organised.

C4 level 3, components of the infrastructure code. One root module composes five reusable modules. A wrapper script picks the environment, so a plan for one environment can never use another's state.

Before the first deployment.

Everything that must be in place before the first deployment. Nothing has been applied to Azure yet, so dev is the first real test.

Tools
Terraform 1.9 or later, Azure CLI to sign in, Bash or PowerShell for the wrapper script, and Git.
Subscriptions
Best one per environment; at minimum production on its own, with dev, QA and UAT sharing one. If they share, turn on enable_service_health_alert and export_activity_log in only one of them. Use a Static Web Apps region (westus2, centralus, eastus2, westeurope or eastasia) and a billing type that supports budgets. The Web, CDN, monitoring, storage and cost services must be registered.
Terraform state
Run bootstrap/ once for the state storage account, then copy its output into each backend.hcl.
Deploying identity
Contributor, User Access Administrator for the monitoring roles, and Storage Blob Data Contributor on the state account.
Settings
In each terraform.tfvars: subscription and tenant IDs, governance tags, alert recipients, viewer and operator groups, and the budget with its contacts, plus custom domains. Replace every <…> placeholder.
Delivery pipeline
After the first apply, store the deployment token as AZURE_STATIC_WEB_APPS_API_TOKEN (one per environment) and the config output as SWA_CONFIG_JSON. Create the GitHub environments or Azure DevOps variable group used for approvals.
Custom domains
Access to the DNS provider to create a TXT validation record and a CNAME per domain. An apex domain needs ALIAS or CNAME flattening.
Front Door Premium
Needed in UAT and production for the managed firewall rules; it is the main cost of this design.
